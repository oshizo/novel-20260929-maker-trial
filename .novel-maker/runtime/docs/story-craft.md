# Story Craft 契約 v1

状態: Plot Planningで、読者が何を楽しめる物語にするか確認するための正本

本書は、男性向けの「小説家になろう」「カクヨム」系Web娯楽ファンタジーを主対象にする。一般文学論や海外脚本術を普遍的な正解として適用しない。作品方針が別の読者体験を明示している場合は作品方針を優先する。

本書は、確定設定、作品方針、作者指示、承認済み上位Plotを上書きする権限を持たない。

文章と言葉は [`language-policy.md`](language-policy.md) に従う。読者が楽しめる内容の候補は [`reader-gratification.md`](reader-gratification.md) を使う。

## 1. 根拠と扱い

設計では次の考え方を使う。

- Web小説では、この作品を読むと何を楽しめるのかを早めに伝える。
- 王道や定番は、それ自体では欠点にしない。
- 序盤で主人公の状況や当面の目的が分かるようにする。
- 関係の変化は、会話、任せ方、頼り方、距離など、本文で分かる行動として示す。
- 長編では、能力だけでなく、関係、生活、信用、知識など複数のものが必要に応じて変わってよい。

これらは人気を保証する公式ではない。固定回数、固定個数、必須配置にはしない。

## 2. 基本原則

### 2.1 意外性より先に、この作品を読むと何が楽しいかを伝える

- `読者への約束` にある主要な楽しみを、序盤で小さくても実際に見せられるか考える。
- 謎、どんでん返し、危機、難しい選択は、作品固有の楽しみを強める場合だけ使う。
- 意外性が弱いことだけを欠点にしない。

### 2.2 作品が約束した複数の変化を忘れない

作品に合う範囲で、たとえば次が変わる。

- 能力・戦術・技能
- 仲間やヒロインとの関係
- 金、装備、住居、食事、旅の自由度
- 社会的信用、仕事の選択肢、地位
- 情報、研究理解、世界理解
- 仲間の能力や役割

すべてを毎回変える必要はない。同じ種類の楽しみを主人公へ繰り返してもよい。

### 2.3 出来事の結果を次の行動へつなげる

戦闘、仕事、訓練、発見などの結果として得たものが、その後の能力、生活、関係、信用、装備、選択肢へどう影響するかを見る。

一つの出来事へ機械的に多くの結果を付けない。自然につながるものだけ使う。

### 2.4 関係の変化は行動で分かるようにする

「信頼が深まる」などの説明だけで終わらせず、前後で何が変わるかを書く。

- 自分から話しかけるようになる。
- 呼び方や距離の取り方が変わる。
- 判断、持ち物、身体の安全などを任せる。
- 助けを頼む、弱みを話す。
- 相手のために自分から役割を引き受ける。
- 一緒に過ごす時間を選ぶ。

固定の恋愛段階へ当てはめない。

### 2.5 各Episodeの役割を決め、毎回同じ種類の満足を要求しない

Episodeには、成功、人物提示、関係変化、生活、問題解決、後で必要になる情報、緊張、喪失、移動など、さまざまな役割があり得る。

毎Episodeへ山場、強い引き、戦闘、読者が満足する場面を必須にはしない。

一方、作品が具体的な成功や関係変化を約束しているのに、それらを長く先送りし続けていないかは確認する。

### 2.6 王道・定番・反復であること自体は欠点ではない

- 読者が期待した楽しみを実際に読めるかを見る。
- 同じ種類の成功や承認を繰り返してよい。
- 条件、相手、難しさ、結果まで毎回同じになり、意図せず単調になっていないかを見る。

### 2.7 主人公が何者で、なぜ動くかを読者が理解して追えるようにする

序盤では、少なくとも次が分かるようにする。

1. 誰が主人公か。
2. 主人公が物語開始時点で何をしており、どんな状況にいるか。
3. 当面何を望み、何を避けるか。
4. なぜ最初の重要な行動や選択をするのか。
5. この主人公を追うと何を楽しめそうか。

長い人物紹介や過去説明を先頭へ置く必要はない。行動、内面、短い状況説明から分かればよい。

重要な入口体験を本文外へ落とさない。主人公の現在、最初の能力提示、中心人物との重要な出会いなど、読者が主人公を理解して追うために必要な出来事は、作品方針に反しない範囲で本文上に置く。

### 2.8 基本となる視点は主人公一人称とする

本書が主対象とする男性向けなろう・カクヨム系Web娯楽ファンタジーでは、明示指定がなければ主人公一人称を本文の基本視点とする。

優先順位:

1. 現在の作者指示。
2. 作品方針。
3. `style/profile.md` 等の継続的な指定。
4. 明示指定がなければ主人公一人称。

視点変更は禁止しない。主人公視点では直接見せられない感情、評価、重要な行動などを示す明確な理由がある場合に使う。視点人物と切替位置は明確にする。

### 2.9 Planning成果物に、読者が楽しめることを残す

Story Craftで考える情報と、Planning成果物へ恒久保存する情報を分ける。

#### Story Craftの確認時に区別して考えること

必要に応じて次を区別して確認する。

1. **読者が楽しめること**: 誰のどんな成功、変化、獲得、扱いなどを楽しめるのか。
2. **誰についてのことか**: 主人公、特定人物、特定人物から主人公への態度、チームなど。
3. **引き継ぎ元**: 上位から任された内容か、その階層で追加した内容か。
4. **先に分かるようにしておくこと**: その出来事を楽しむため、事前に読者が知る必要があること。
5. **何が起きるか**: その範囲の粒度で起きる成功、選択、獲得、関係変化など。
6. **その後どう変わるか**: 能力、関係、生活、信用、装備、情報、選択肢などに残る変化。

これは確認観点であり、六項目をすべて各Planning成果物へ別fieldとして保存する契約ではない。

#### Planning成果物へ保存するときの原則

- 各階層のtemplateで責務を持つ場所へ、必要な結果だけを保存する。
- 同じ事実、変化、仕込みを複数sectionへ言い換えて保存しない。
- 別sectionから同じ情報が必要な場合でも、説明を再掲せず、そのsection固有の差分だけを書く。
- Story Craft Challengerの確認用メモや中間整理を、恒久成果物へそのまま残さない。

Overallでは次を正本位置とする。

- 作品全体として何を楽しませるか -> `読者に何を楽しませるか`
- 主人公、主要関係、能力、生活、知識、選択肢などの長期変化 -> `中心となる対立と長期変化`
- どのArcで何を進めるか、どのArcで後のための情報を示すか -> `Arc一覧`

このためOverallの `読者に何を楽しませるか` へ、Arc配置、前振り一覧、長期変化を重複して保存しない。

Arc / Episodeでは各templateが要求する粒度に従う。下位ほど本文に近い具体性が必要になるため、Overallと同じ保存欄数にそろえる必要はない。

緊張、謎、危険、人物の有能さを、無理に「今回読者が満足する内容」として扱わない。

### 2.10 後の楽しさに必要なことを先に示す

後で成功、承認、恋愛進展、獲得などを描くとき、その出来事がなぜ嬉しいのか読者が理解できるよう、必要な情報を先に示す。

必要に応じて次を扱う。

- 課題の難しさや通常の基準。
- 主人公や仲間の制約。
- 何が不足しているか。
- 得たいものがなぜ必要か。
- 認める人物がどんな基準を持つか。
- 親しくなる相手がどんな人物か。
- 反撃する相手が何をしたか。

後の出来事と関係しない情報を、型を満たすためだけに追加しない。

前振りを考えることと、前振り専用sectionを必ず作ることは別である。Overallでは、必要な前振りを実際に示すArcの `後のためにこのArcで示すこと` へ置く。

### 2.11 Planning階層は、上位を引き継ぎつつ各範囲で必要なら追加する

Overall → Arc → Episodeは、上位の一覧を単純に細かく分ける関係にはしない。

1. 上位で下位へ任せた内容は下位で消さない。
2. 下位は、その範囲だから分かる楽しみを追加してよい。
3. 追加は上位条件と矛盾しない範囲に限る。
4. 各階層で必ず追加するという件数条件は設けない。
5. 下位で追加した内容を上位へ自動的に書き戻さない。
6. 下位で追加した内容が上位の物語の意味を変えるほど大きい場合は、上位の再検討が必要か親agentへ返す。

## 3. 変更してはいけない上位条件

Story Craft Challenger / Planner Revisionは、次を上書きしてはならない。

1. 作品方針の `読者への約束` / `必ず守る方向` / `避ける方向`。
2. 確定設定。
3. 現在の作者指示のうち作者側の制約として確定したもの。
4. 承認済み上位Plotの固定条件。
5. 対象Episodeに適用されるStyle上の視点指定。

面白さを増やすために、既存条件から導けない大前提を勝手に追加しない。必要なら設定提案または作者判断として扱う。

## 4. 対象ごとの確認観点

### 4.1 Overall Craft

Overallでは、作品全体で読者が何を楽しめるかを見る。

- 作品方針の主要な `読者への約束` が、具体的な出来事や長期変化へつながっているか。
- 主人公、主要関係、生活、成長、対立、長期変化から、Overallで追加した方がよい楽しみがあるか。不要なら追加しない。
- 誰についての楽しみかが分かるか。
- 必要な前振り、主に何が起きるか、その後の変化が、Arc一覧や長期変化の正本位置から確認できるか。
- 序盤で主要な楽しみを小さくても実際に見せられるか。
- 主人公の開始時の状況、当面の選択、長期変化が分かるか。
- 能力、関係、生活、装備、信用、知識など、作品が約束した複数の変化を忘れていないか。
- 同じ事実、変化、仕込みを複数sectionへ重複保存していないか。
- Arc一覧を、Arcで追加できる内容の上限にしていないか。

Overallで一回の台詞、細かな場面順、個別の戦術手順まで決めない。

### 4.2 Arc Craft

Arcでは、数Episodeを通じて何が起き、終了時に何が変わるかを見る。

- 親OverallからこのArcへ任された内容を落としていないか。
- Arc固有の目的、相手、障害、生活、関係、終了時の変化から、このArcだから成立する楽しみを必要なら追加しているか。
- このArcで実際に楽しませることと、後のために先に示すことを混同していないか。
- 誰についてのことか、先に何を知る必要があるか、何が起きるか、その後どう変わるかが分かるか。
- このArcでは結果を出さない内容を、無理にその場の満足として扱っていないか。
- Episode一覧を、Episodeで追加できる内容の上限にしていないか。
- 一回の台詞、細かな場面順、観察対象、技の使用順序、戦闘手順などをEpisode Designへ残しているか。

### 4.3 Episode Craft

Episodeでは、その回が何を担い、どのような出来事を読者が読むかを見る。

- 親ArcからこのEpisodeへ任された内容を落としていないか。
- 個別の場面、状況、会話、生活、小さな成功や獲得から、このEpisodeだから成立する楽しみを必要なら追加しているか。
- 成功を見せる回なのか、緊張、喪失、移動、情報提示などを主に扱う回なのかが分かるか。
- その回で実際に楽しませることと、後のために先に示すことを混同していないか。
- その回で読者が満足する出来事がなくても、役割が成立していれば許容しているか。
- 入口と出口で能力、関係、生活、情報、問題状態の何が変わるか。
- 関係の変化を扱う場合、会話、選択、距離、任せ方などの行動として分かるか。
- 視点人物が明確か。

Episode Designの作者向け説明は、そのまま執筆指示へ移さず、本文で扱える行動、状態、情報へ変換する。

## 5. Story Craft Challengerの役割

Story Craft Challengerは、技術上の整合性を確認するReviewerではない。

主に次を確認する。

- 上位から任された楽しみや、後のために先に示す内容が下位で失われていないか。
- 下位で追加できる内容を、上位に同じ項目がないという理由だけで削っていないか。
- 読者が楽しめることとして書かれた内容が、実際には出来事の種類、人物の品質条件、緊張、謎だけになっていないか。
- 後のために先に示す内容を、今回の満足として扱っていないか。
- 必要な前振り、実際の出来事、その後の変化がPlot上に存在するか。
- 誰についての楽しみかが別の対象へ変わっていないか。
- Overall / Arcが下位で決めるべき細部まで決めていないか。
- Story Craftの確認用情報を、必要以上にPlanning成果物へ複製していないか。

出力は次の四種を基本とする。

- `維持`: 改訂で壊すべきでないもの。
- `不足`: 上位条件を満たしていない、必要な出来事や前提がないなど、Planner Revisionで原則として対処すべきもの。
- `改善候補`: 上位条件は満たしているが、比較的高い確度で改善できるもの。
- `仮説`: 有望だが作品固有の好みや詳細設計に依存するもの。

長い案出しをせず、価値が高い改善を優先する。新設定を足すより、既存の出来事や結果の組み合わせ、順序、役割を見直す。

## 6. Planner Revisionの役割

Planner RevisionはChallengerの指摘をすべて採用する工程ではない。ただし `不足` は単なる好みの提案として扱わない。

1. `維持` を保護する。
2. `不足` を先に確認し、上位条件と矛盾しない限り解消する。
3. 解消できない `不足` がある場合は理由を親agentへ返す。
4. `改善候補` / `仮説` から価値の高いものを選ぶ。
5. 採用した内容だけを `採用した改善意図` として次工程へ渡す。
6. 改訂したPlotに合わせて、各templateで責務を持つ正本位置だけを更新する。

Story Craftの確認用に考えた前振り、出来事、結果の残り方を、同じ意味の説明として複数sectionへ展開しない。

下位で追加した内容を上位へ自動的に書き戻さない。

## 7. Technical Reviewer / Finalizerとの境界

Planner Revision後にTechnical Reviewerが確認する。

Technical Reviewerの主な責務:

- 作品方針 / 確定設定 / 上位Plotへの適合。
- 因果、視点と情報開示、前後の整合、人物の主体性。
- 後で使う情報、設定提案、status、version、依存関係。
- Planning成果物に書かれた内容が、実際のPlotと矛盾していないか。
- 上位から引き継いだ内容が消えていないか。
- 下位で追加した内容を、上位に同じ項目がないという理由だけで削っていないか。
- 同じ意味の情報が複数sectionへ重複保存されていないか。
- 自然で平易な日本語になっているか。

Technical Reviewerは新しいStory Craft案を発明しない。

Finalizerは次の順で扱う。

1. 変更してはいけない上位条件。
2. 技術上の必須修正。
3. 採用した改善意図。
4. 技術上の改善提案。

重複を直す場合は説明を足して整合させず、正本位置を決めて統合・削除・移動する。

作者が読む成果物の自然な日本語を保ち、意味を短い設計用語へ置き換えない。

## 8. Story Craft Regression

Finalizer後、採用した改善意図が技術修正で弱まっていないか確認する。

確認すること:

1. 採用した改善意図が弱くなったり消えたりしていないか。
2. 読者が楽しめること、誰についてのことか、引き継ぎ元とPlotの対応が弱くなっていないか。
3. 必要な前振り、実際の出来事、その後の変化が、責務を持つ正本位置から消えていないか。
4. 上位から引き継いだ内容が消えていないか。
5. 下位で追加した内容が、上位に同じ項目がないという理由だけで削除されていないか。
6. Overallで重複を一つの正本位置へ統合した結果、必要な意味まで消えていないか。

Overallで重複を統合する修正、Overallで細部をArcへ戻す修正、Arcで細部をEpisode Designへ戻す修正自体は問題にしない。必要な意味が保たれていればよい。

出力:

- `PASS`
- 狭い範囲の回帰指摘

ここでは新しい改善案を追加しない。

## 10. 非ルール

次をframeworkの普遍的な必須条件にしない。

- 毎話ざまぁ。
- 毎話強い引き。
- 毎話必ず戦闘。
- 毎話必ず読者が満足する出来事を一つ以上入れること。
- 各階層で必ず新しい楽しみを一つ以上追加すること。
- 読者が楽しめる内容を固定個数だけ選ぶこと。
- 主人公以外の仲間・チーム・共同体へ必ず分散すること。
- 主人公へ同じ種類の楽しみを繰り返すことを避けること。
- 下位Planningの内容を上位Planningの一覧だけに限定すること。
- 下位で追加した内容を上位成果物へ必ず書き戻すこと。
- 主人公最強。
- 苦戦禁止。
- N話ごとに恋愛進展。
- 各Arcにどんでん返し、裏切り、難しい選択を一つずつ入れること。
- 三幕構成、Hero's Journey、Save the Cat等の固定構成。
- 一般的なファンタジー要素の存在自体を欠点扱いすること。

作品固有の作品方針がこれらを求める場合だけ、その作品では制約になり得る。
