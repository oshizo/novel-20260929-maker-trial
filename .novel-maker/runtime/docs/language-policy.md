# 記述言語と日本語表現の規約

状態: framework文書・story template・agent指示・作品成果物に共通する記述規約

このリポジトリの文書やagent指示は、そのまま計画作成や本文生成を行うモデルの入力になる。したがって、文書の日本語そのものを生成品質の一部として扱う。

## 1. 基本方針

人間または生成モデルが読む説明文は、**自然で平易な日本語**で書く。

英語表記を残してよいのは、表記自体に意味があるものに限る。

- ファイル名、パス、コマンド名、識別子、schemaのfield名
- `draft`、`ready`、`stale` など機械が扱う状態値
- Git、Issue、Pull Request、Markdown、YAMLなど一般にその名前で扱う技術用語
- model名、製品名、ライブラリ名などの固有名詞
- Overall、Arc、Episodeなど、このframeworkで構造単位として定着している名称

人間が読む見出し、説明、箇条書き、表の列名は、内部実装の識別子をそのまま転記せず、意味が直接分かる日本語にする。

## 2. framework内だけで通じる言葉を作らない

一般的な日本語で説明できる内容に、新しい専門語、略語、抽象的な呼び名を付けない。これは成果物だけでなく、ガイド、agent指示、内部で考えるための説明にも適用する。

概念を短い名前へ置き換えるより、何を確認するのかを普通の文章で書く。

- 誰についての話か。
- 何が起きるのか。
- その人物は何を知り、何を考え、何を選ぶのか。
- その出来事の前に、読者が何を知っている必要があるのか。
- 出来事の後で、能力、関係、生活、情報、選択肢などの何が変わるのか。

設計文書だから抽象的な言い回しを許す、という扱いにはしない。設計文書ほど、後工程がそのまま参照しても意味がずれない言葉を使う。

## 3. 一般的な語の組み合わせを使う

単語が辞書に載っているだけでは十分ではない。名詞と動詞、名詞同士、修飾語と被修飾語の組み合わせとして、一般的な説明文で自然に使われる形を選ぶ。

次の状態になった文は書き直す。

- 単語ごとの意味は分かるが、文全体の意味を読み手が推測しないと理解できない。
- 抽象名詞を、何にでも使える動詞で処理している。
- 名詞を連結しすぎて、誰が何をしたのか分からない。
- 元の設定やPlotを読み直さないと、文が指す具体的な出来事が分からない。

迷った場合は、主語と具体的な動作を戻す。短くすることより、普通に読んで一度で意味が分かることを優先する。

## 4. Planningでは比喩を使わない

Overall、Arc、Episode Design、Planning用ガイド、Plannerへの指示では、説明のための比喩を使わない。

人物、出来事、理由、結果、変化を、そのまま書く。ゲーム、商取引、機械、建築、身体など別の分野になぞらえて説明しない。

作品世界の固有名詞や、作中人物が実際に使う比喩表現まで禁止する規則ではない。ここで禁止するのは、**計画を説明するために作者側が使う比喩**である。

## 5. 一行へ縮めない

Planning成果物には、字数や一行当たりの長さの上限を設けない。別の規約や作者指示で明示されていない限り、短くすること自体を目標にしない。

複数の出来事、理由、判断、結果がある場合は、複数文または箇条書きへ分ける。

表は次のような短い値を並べる場合だけ使う。

- 識別子
- 状態
- version
- 短い参照先
- 一語または短句で十分な分類

一つのセルに複数文の説明が必要になる内容は、表ではなく小見出しと箇条書きを使う。OverallのArc一覧、ArcのEpisode一覧、人物や関係の長期変化なども、説明量が多いなら同じ扱いにする。

## 6. 本文に近いほど、具体的な言葉を使う

Episode Designから執筆指示へ進むほど、作者側の設計上の言葉を減らす。

執筆指示には、本文で扱える次の情報を中心に残す。

- 人物、場所、物、身体、環境の状態
- 視点人物が知っていること、考えていること
- 人物が行うこと、話す内容
- 情報が明らかになる時期
- 前後の因果や継続を守るために必要な条件

作者側の説明用ラベルや、読者にどう感じてほしいかという抽象的な指示を、そのまま本文執筆担当へ渡さない。

## 7. 本文の既定方針

このframeworkが主対象とする男性向けWeb娯楽小説では、作品方針、作者指示、Styleで別の指定がない限り、**本文でも比喩を使わない**。

文学的な言い換えで印象を強めるより、視点人物が見たもの、感じた身体感覚、考えたこと、行動したことを具体的に書く。

作品固有のStyleとして比喩表現を明示的に採用する場合は、その指定を優先してよい。

## 8. agent指示の書き方

`developer_instructions` もこの規約に従う。

- 内部で考えるためだけの擬似専門語を作らない。
- 判断条件は、何を見てどう判定するのかを普通の日本語で書く。
- 悪い表現の長い一覧をPlannerやWriterへ与えない。
- Reviewerや回帰テストが不具合の実例を持つことは許容する。ただし、それをPlannerやWriterが読むruntimeへ流さない。

## 9. 変更時の確認

framework文書、agent指示、story templateを変更するときは、少なくとも次を確認する。

1. 一般的な日本語で書ける内容を、英語や新しい概念名へ置き換えていないか。
2. 名詞と動詞の組み合わせが、一般的な説明文として自然か。
3. 設計文書だけで通じる抽象表現が残っていないか。
4. Planning用の説明に比喩が入っていないか。
5. 説明量の多い内容を、表の一セルや一文へ押し込んでいないか。
6. 本文へ近い入力ほど、人物、行動、状態、情報を具体的に書いているか。
7. 不具合の実例を、必要のないPlanner / Writer入力へ混ぜていないか。

目的は用語を機械的に禁止することではない。**ガイド自身を含め、生成モデルが読む前例を自然で分かりやすい日本語にそろえること**を目的とする。
