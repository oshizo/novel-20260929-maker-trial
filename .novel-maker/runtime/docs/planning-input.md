# Planning入力契約 v1

状態: `plan overall` の前に行う入力整理と開始条件の正本

Plotの作成・確認・再計画は [`plot-planning.md`](plot-planning.md)、repositoryの所有境界は [`repository-contract.md`](repository-contract.md)、文章と言葉は [`language-policy.md`](language-policy.md) に従う。

Planning中にCanon・上位計画を補う場合と、作品入力を途中変更した場合は [`planning-changes.md`](planning-changes.md) に従う。保存先がCanonや上位であることだけを理由に、現在のPlannerの創作判断を親へ返さない。

## 1. 目的

Overallを作る前に、作品固有の入力をAIが自走できる状態へ整理する。

「設定が足りない」という理由だけで作者へ質問しない。まず次の三点を確認する。

1. **作者側の目的が足りないか**  
   読者への約束や大きな制約がなく、何を良いOverallとするか判断できない状態ではないか。
2. **主人公の最低限の前提が足りないか**  
   誰を主な主人公として追い、物語開始時点でどんな人物・状況から始まるか分からない状態ではないか。
3. **情報の置き場所が間違っていないか**  
   確定設定へ未来のPlot案や作者側の理由が混ざり、Plannerが創作ではなく清書だけをする状態になっていないか。

AIが決めてよい創作事項はAIが決める。後で決めてよい事項は後へ回す。作者側の目的そのものが足りない場合だけ作者へ返す。

## 2. 各正本の役割

### 2.1 作品方針

作品として何を狙うかを表す作者側の目的・制約を置く。作中で既に成立している事実ではない。

正本はstory repo rootの `story-direction.md`。

入れてよいもの:

- 何の物語を始めるかという最小限の前提
- 読者への約束: 何を読んで楽しい作品か
- 雰囲気、規模、関係性の方向
- 結末の大きな方向
- 作者が必ず守りたいと決めた高位の結果
- 作品を別物にするため避けたい方向

入れないもの:

- AIが設計すべきEpisode順や場面の答え
- Reviewerが一時的に出した局所的な修正案
- 世界・人物の成立済み事実
- 文体の指示

### 2.2 確定設定

将来の本文でも守る、継続的な作中事実と規則を置く。

入れてよいもの:

- 過去・現在の人物事実
- 物語開始時点の主人公の立場、生活、状況、変わりにくい性格・制約
- 能力、世界、制度、物理条件の規則
- 固有名詞・固定用語
- 将来のPlotを制約するが、それ自体は未来の出来事ではない規則

原則として入れないもの:

- 未来の出来事や順序
- 「第3Arcで加入に失敗する」のようなPlotの答え
- 作者側の理由や、読者にどう感じてほしいかという指示
- 推奨場面、仕込みと回収、Episode案

元資料で `[FIX]` と書かれていても、意味が未来の出来事なら確定設定にはしない。

### 2.3 Planning

具体的な未来の出来事、順序、仕込みと回収を置く。

Overall生成前に作者が具体的な未来の出来事を固定している場合は、作品方針の必ず守る方向として入力し、Overall生成時にPlanningへ落とす。

### 2.4 Style

本文の文体、基本視点、人称など、本文全体へ継続して効く書き方の指定を置く。

### 2.5 State

現在地点の人物状態、知識、関係、未回収事項など、執筆を再開するための現在情報を置く。

## 3. 作者入力の保存先

`Human Direction` のような巨大な別置き場は作らない。

現在の作者指示はその実行の入力として受け、将来も残す必要がある内容だけを意味に応じて正本へ保存する。

| 作者入力 | 保存先 |
|---|---|
| 作中の成立済み事実 | `canon/` |
| 作者側の目的 / 読者への約束 / 高位の制約 | `story-direction.md` |
| 具体的な未来の出来事 / 順序 | `planning/`。Overall前なら必ず守る方向として一時的に渡し、Planningへ落とす |
| 文体 / 基本視点 / 人称 | `style/` |
| 現在の人物知識 / 状態 | `state/` |
| 上記へ置けない横断判断 | `state/decisions.md` |

AIが上位Plotやreviewから導いた一時的な指針を、作者が確定した判断として扱わない。

## 4. 入力整理

Planning Readinessを判定する前に、入力の置き場所を確認する。

最低限、次を見る。

- 確定設定に未来のPlotの答えが混ざっていないか。
- 作者側の理由や一時的な修正指示が確定設定へ入っていないか。
- 作者指示のうち継続して残す内容が適切な正本へ保存されているか。
- 作品方針へ具体的なPlotの答えを入れすぎ、Plannerの自由を奪っていないか。
- 既存Planningを作品方針や確定設定として重複定義していないか。

置き場所の誤りが明らかで、意味を変えずに移せる場合はAIが直す。そのためだけに作者確認を挟まない。

旧repositoryから移行するとき、`[FIX]` / `[WIP]` / `[GUIDANCE]` / `[RATIONALE]` 等のタグは参考にしてよい。ただし保存先はタグ名ではなく内容の意味で決める。

## 5. いつ決めるか、誰が決めるか

### 5.1 今決める必要があるか

- `required-before-overall`: Overallの主要因果、読者への約束、または物語開始時の主人公理解を成立させるため、Overall前に決める必要がある。
- `defer`: Arc / Episodeまで未確定でよい。

### 5.2 誰が決めるか

`required-before-overall` の項目について:

- AIが創作判断として決められるものは作者へ質問せず決める。
- 作者側の目的・価値判断そのものは作者判断または明示的な委任が必要。

作者が「そこも任せる」と委任した場合はAIが決めて進む。

### 5.3 作者へ質問する条件

原則として次をすべて満たす場合だけ作者へ返す。

1. 現在のPlanningに不可欠で、決めないと作品の主要方向が定まらない。
2. 欠けているのがPlotの具体化ではなく、読者への約束、関係性の方向、結末の方向など作者側の目的に近い。
3. 既存の作品方針から合理的に決められない。
4. 作者から包括的な委任を受けていない。

複数の良いPlot案があるだけでは質問しない。AIが選ぶ。

### 5.4 主人公の最低限の前提

Overallを作る前に、少なくとも確定設定 / 作品方針等から次を識別できること。

- 誰が主な主人公か。意図的な群像劇なら、その形式自体が分かること。
- 物語開始時点で、その人物がどういう立場・生活・状況にいるか。
- 最初の重要な選択を理解するために必要な、変わりにくい性格・立場・制約。

長期大目標、夢、使命は必須ではない。流され型・巻き込まれ型でもよい。必要なのは、「何者か分からない人物が理由不明のまま最初の重要行動を取る」状態を避けるための最小限の足場である。

不足している場合は次のように扱う。

```text
主人公の最低限の前提が不足
  ↓
作者の価値判断なしでAIが決めてよい？
  ├─ YES → Planning readiness: foundation-required
  │          判定役が最小限の補完案と保存先を返す
  │          親agentが確定設定等へ保存
  │          Planning Readinessを再実行
  │
  └─ NO / 作者側の目的そのものが必要
           → Planning readiness: needs-author-direction
```

Planning Readinessを担当するagentがread-onlyでも、`foundation-required` では作者へ質問しない。親agentが保存できるように、必要最小限の事実、保存先、既存入力からの根拠を返す。

ここで補うのは継続的な現在・過去の人物事実である。Episode順や未来の出来事を先回りして確定設定へ書かない。

## 6. 固定質問票にしない

Planning開始前に、人物設定や世界設定をすべて埋める方式にはしない。

次のような項目を機械的に全部質問することを禁止する。

- 主人公の年齢
- 主人公の職業
- 主人公の全過去
- 主人公の長期目標
- 全何章か
- 敵は誰か
- 結末詳細
- 各人物のArc
- 全世界設定

主人公の最低限の前提も、人物プロフィール全欄を埋めるためのものではない。物語開始時の主人公と最初の選択を理解できる最小限だけをOverall前に要求する。

0問で `ready` ならそのまま `plan overall` へ進む。

Planning Readinessは「すべての設定が埋まっている」ことを意味しない。

## 7. Planning Readinessの出力

通常の事前確認は最低限、次の形でよい。

```text
入力整理:
  - 自動で移した内容 / 問題

Planning readiness: ready / normalization-required / foundation-required / needs-author-direction

十分に分かっていること:
  - ...

今決める必要があり、AIが決められること:
  - ...

主人公の前提補完:
  - 保存先: ...
  - 最小限の事実: ...

後で決めてよいこと:
  - ...

作者判断が必要なこと:
  - ...  # 空なら作者質問不要
```

`normalization-required` は、明白な置き場所の誤りを現在の作業内容へ反映してから再評価する。

`foundation-required` は、AIが決められる主人公の最低限の前提を現在の作業内容へ保存してから再評価する。作者へ返さない。

`needs-author-direction` の場合だけ作者へ返す。

作者回答後は、将来も残す内容を適切な正本へ保存し、Planning Readinessを再評価してからOverall生成へ進む。

## 8. `story-direction.md` の推奨形

```markdown
# 作品方針

## 物語の出発点

<何の物語を始めるか>

## 読者への約束

- <何を読んで楽しい作品か>

## 必ず守る方向

- <必ず守る高位の方向>

## 避ける方向

- <作品を別物にするため避けたい方向>
```

空欄を埋めるために情報を捏造しない。不要な節は削ってよい。

## 9. Overall開始条件

Overallを作る前に、少なくとも次を満たす。

- 入力の置き場所を整理済み。
- 作品方針と確定設定から、物語の出発点、読者への約束、大きな制約を理解できる。
- 主人公の最低限の前提が継続的な正本へ保存済み。
- 作者判断が本当に必要な未解決事項がない、または作者がAIへ委任済み。
- Planning Readinessが `ready`。

`normalization-required` / `foundation-required` / `needs-author-direction` のままOverallへ進まない。

## 10. 作者確認との責務分離

Planning Readinessで作者へ求めるのは、AIが決められない作者側の目的だけである。

主人公の最低限の前提が不足していても、既存の作品方針からAIが決めてよいなら作者へ質問せず保存する。

Overall / Arc生成後の作者確認は主に、作品として採用したいか、作者の好みに合うかを確認する。因果、確定設定との整合、仕込みと回収等の技術確認はReviewer / Finalizer側の責務であり、作者がsystem側の確認表を診断できることを前提にしない。
